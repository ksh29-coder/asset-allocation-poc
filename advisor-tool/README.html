The advisor tool exercise

Four AI models get the same brief, the same client, and ten minutes each. You compare what they built.

What this is

Each of the four folders here is a sealed copy of one exercise. Inside each is the brief below, a fund shelf, and a real client portfolio — nothing else. Four models were given one folder each and ten minutes.

The exercise is not "who built the most". It is what each model chose to build, what it refused, and whether the numbers hold up when you check them.

The briefing they were given

Build a tool that helps a client advisor manage this client's portfolio better.

That is the whole of it. Nothing more specific is coming — working out what "better" means for this client, and what an advisor actually needs in front of them, is the job being handed to you.

A workshop with the advisers produced ten asks.

Nobody has sorted them, costed them, or argued about which matter.

  1. What the client holds today: what it is, and what it costs them in dollars.
  2. How the portfolio has actually performed, and over what period.
  3. What it is concentrated in, and whether that should worry anyone.
  4. The current book compared against an alternative built from the same shelf.
  5. Where the risk actually sits — which holdings drive the volatility.
  6. The worst it has been, and how long it took to recover.
  7. What the client pays in fees over the next fifteen years if nothing changes.
  8. Cheaper ways to hold the same exposure, and what the saving is worth.
  9. What a proposed change costs to execute: turnover, and the gains it realises.
  10. What date range every figure covers, and why that range.

Ten items of this size cannot be built in ten minutes, and the brief says so. Deciding which of them matter is the actual test. The brief also sets four rules:

  • Use only the data you are given. No invented account sizes, yields or rates. Anything resting on an assumption must show that assumption on screen, where the adviser can change it.
  • Prove one number. Put a check on the page that would fail if the arithmetic were wrong — and show the result, including when it fails.
  • The screen is the deliverable. Nobody will read the code, but the numbers it produces will be checked.
  • Ten minutes, self-timed. The model reads the clock itself and stops. Stopping is its job, not ours.

The client

Account$2.4m, taxable
Holdings9 funds, from a fixed shelf of 16
Unrealised gain$312,000 — so selling has a tax cost
Horizon~15 years from drawing on the money

Everything the models show must come from the three files in data/. They are told not to invent inputs, and to label any assumption on screen.

How to run it

Check the workspaces are provisioned — this changes nothing, it only verifies:

cd advisor-tool
./preinstall.sh --check

Then start each model's tool. They can all run at once, so you can flip between tabs:

cd claude-opus && ./run.sh serve     # prints its URL
cd glm         && ./run.sh serve
cd inkling     && ./run.sh serve
cd kimi3       && ./run.sh serve

Each workspace has its own port range: claude-opus 7600, glm 7900, inkling 7800, kimi3 7700. Each also leaves a SUMMARY.html saying what it built and why, with a link straight through to its running page — that is the quickest way in.

Two practical things. Plug the laptop in, or run caffeinate — a previous session lost 37 minutes to the machine sleeping mid-build. And avoid ports 5000 and 7000; macOS AirPlay holds both.

What to look for

  • Would you let an advisor take this into a client meeting on Monday? That is the whole test.
  • What did it refuse to build, and do you agree? Declining an ask can be the better answer — three of four refused to compare against an invented alternative, and were right to.
  • What is this client paying? Some tools tell you in dollars, some only in percentages. Only one of those answers the question a client asks.
  • Pick the most impressive number on any screen and ask where it came from. Not all of them can tell you.

Running it again

Only the setup is kept here — the brief, the data, and the installed toolchain. What the models produced has been cleared, so the folders are ready for a fresh run. Give each model one workspace and nothing else; the brief tells it that its folder is the entire world.

Marking a run. There is a judge skill in this repo that assesses a completed run — it carries the answer key, the reference figures, and the traps that have separated the field every time. Its first rule is worth knowing even if you mark by hand: never mark from a model's own summary. Every run so far has produced at least one summary that misstates its own work.
