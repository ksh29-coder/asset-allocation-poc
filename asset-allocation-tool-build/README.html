The asset allocation platform exercise

Four AI models get the same fund shelf, the same price history, and a brief that deliberately refuses to say what to build. You compare what they made of it.

Each of the four folders here is a sealed copy of one exercise. A model is given one folder and nothing else. Every model starts from an empty page and a list of sixteen funds, and the first thing it has to decide is what an allocation tool is for.

1 · The data they are given

Two files, and nothing else. No internet at runtime, no market feed, no benchmark.

FileWhat is in it
products.csv16 real JPMorgan ETFs — the entire investable universe, with asset class, category, region and published expense ratio
prices.csv17,604 daily closing prices, Aug 2021 to Aug 2026, adjusted for distributions — so returns are total-return, with income already inside them

The shelf spans five asset classes. Fees run from 0.07% to 0.50%, a seven-fold spread, so what a portfolio costs is a real design decision rather than a footnote.

The funds do not all have the same history: seven go back to the start of the price file, nine launched later, and three of those only in 2023. One fund stops six weeks before the rest. The data notes spell this out for the models.

Deliberately absent: no benchmark, no risk-free rate, no tax rate, no account size. Any tool showing a Sharpe ratio or a dollar balance is showing you its own assumption, which is fine — as long as the screen says so.

2 · What we ask the models to do

Build a portfolio management application for building and monitoring client asset allocations from this fund shelf.

The brief is deliberately open. We hand over no feature list — each model has to work out what a professional allocation tool should do for an advisor, decide which features matter most, and build those well.

Four things are required.

Everything else — which features, which language, which architecture — is the model's own call.

  1. A complete working web application, interface and server, that an advisor could use in a browser.
  2. Built entirely on the provided data, working offline once installed.
  3. Tested — a test suite the model would stand behind, which fails loudly rather than quietly.
  4. A SUMMARY.md for a senior non-technical reader: what it built, why each feature helps an advisor, what it left out, and what it would do next.

Three conditions shape the rest:

  • Depth beats coverage. The brief says so in as many words — a few features built well beat many built shallowly.
  • Three commands, and they must work for a stranger. setup, serve, test — nothing else needs to be known about how a build works inside.
  • Handle the real data conditions. The brief calls this "a professional tool, not a happy-path demo," and points straight at the short fund histories.

There is no time limit. The exercise is open-ended, so a thin result has no excuse behind it.

3 · What we expect from the results

Not feature count. A model that builds four things it would stake its name on beats one that builds nine it would not — and since the brief told them so, a sprawling shallow build is a failure to follow instructions as well as a weak tool.

Never judge from a model's own SUMMARY.md. A summary is what the model believes it built, which is not always what it built — the two can diverge without the model noticing. Read the summaries for reasoning, which is the most interesting content. Then check every number against the running application.

Six questions to put to each build:

  1. Would you let an advisor build a client portfolio in this on Monday? That is the whole test, and a non-engineer is better placed to answer it than an engineer.
  2. Does every figure say what period it covers? Given these ragged histories, a performance number without a stated window is probably wrong. Check which window the tool chose, whether it says so, and whether it is the same window everywhere.
  3. What does the portfolio cost, in money? Fees span sevenfold here. A tool answering only in percentages has not answered the question a client asks.
  4. Does it take a view, or only display? "Building and monitoring" implies doing something. A tool that draws charts and leaves every decision to the advisor has moved the work, not reduced it.
  5. Does ./run.sh test actually fail? Run it, break something, run it again. A suite that reports success over a broken application makes every other claim unverifiable.
  6. What did it refuse to build, and do you agree? Declining is often the better answer, and the reasoning behind a refusal tells you how well the model understands the problem.

Two checks worth doing by hand:

  • Pick the most impressive number on any screen and ask where it came from. Not all of them can tell you.
  • Put 100% into a fund that launched in 2023 — JGLO, HELO or JBND — and see what the tool reports over a five-year period. Anything returning a confident five-year figure for a fund that is two years old is telling you something untrue, and it will be telling you the same untruth everywhere else.

Marking a run. There is a judge skill in this repo that assesses a completed run. It verifies every claim against the running service and the source data rather than against the model's own summary.
